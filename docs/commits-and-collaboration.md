# 提交规范与人机协作说明

> 对应 V3 方案「CodeArts 留痕」第 7 项：一页人机协作说明，证明真实使用 CodeArts 代码智能体，而非"假用工具"。
> 适用：本仓库全部 Git 提交。版本库基线于 2026-10-31 建立。

## 一、分支策略

| 分支 | 用途 |
|---|---|
| `main` | 稳定可运行版本，始终保持可构建、可复现答辩效果 |
| `feature/<模块名>` | 新功能开发，完成并自测后合入 `main`（当前阶段直接在 main 提交，后续按需拆分） |

## 二、提交信息格式

```
<type>(<scope>): <subject> [<协作标记>]
```

- `type`：`feat`（新功能）、`fix`（修复）、`docs`（文档）、`refactor`（重构）、`test`（测试）、`build`（构建/依赖）、`chore`（杂项）
- `scope`：涉及模块，如 `server`、`frontend`、`map`、`db`、`rag`、`harmony`
- `subject`：简明陈述"做了什么"，使用中文

## 三、协作标记（必带，便于核查人机比例）

| 标记 | 含义 |
|---|---|
| `[AI]` | 代码由 CodeArts 智能体生成，人工仅做审查与确认 |
| `[人工修改]` | 人工在 AI 产物基础上实质修改，或完全手写 |
| `[AI+人工]` | AI 生成与人工修改均占明显比例，需在开发日志注明人工改动点 |

示例：
- `feat(db): 新增 MySQL 连接池与优雅降级 [AI]`
- `fix(rag): 修正向量归一化导致的召回排序错误 [人工修改]`
- `docs: 更新部署检查清单 [AI]`

## 四、人机协作流程留痕

1. 每个模块在 CodeArts 中以"需求描述 → 生成 → 验证 → 迭代"的对话推进，关键节点记录于 `docs/codearts-development-log.md`。
2. 构建失败、修复前后对比是重点留痕材料，需在开发日志保留问题与处理方式。
3. 云服务（RDS/Redis/OBS）的开通与部署通过 CodeArts Skills 完成，保留操作截图与日志（部署阶段进行，当前阶段不涉及）。
4. 密钥、连接串、`.env` 一律不入库（根 `.gitignore` 已拦截），仅通过环境变量注入；仓库提供 `.env.example` 说明所需变量。

## 五、可复现承诺

- 仓库内不包含任何仅存在于作者本机的隐式依赖；新增依赖必须写入对应 `package.json`。
- 克隆后按各模块 README / 文档步骤即可安装、构建并复现答辩演示效果。
- 数据库、缓存、模型等外部组件在缺失时统一降级到内置实现，保证最小路径仍可运行。
